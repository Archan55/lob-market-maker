# Finite offline reconciliation, version 1

This PR2 extension recovers available execution detail after missing reports or
uncertain order outcomes. It remains a constructed, offline research protocol.
The no-recovery baseline is pinned at
`ff65d453e53292d48e425107de269a3f5466573d`; PR1 remains unchanged at
`d4104b70660976c6d59fe8915a75ac5616bdecd3`.

## Policy and three clocks

`run_backtest(..., reconciliation=ReconciliationPlan(...))` requires finite
`client_stop` with mark accounting. Its immutable schedule contains 1–16 strictly
increasing query times, each between stop and the inclusive observation horizon.
Queries ask for every locally sent client order ID, including orders whose
terminal acknowledgment arrived but whose execution detail may be incomplete.
YAML, CLI and ordinary backtests retain their previous behavior.

| Time | Meaning |
|---|---|
| `request_timestamp_ns` | Client sends a query; no venue knowledge becomes available yet |
| `exchange_snapshot_timestamp_ns` | Query reaches the simulated venue after request latency; immutable response is built from the journal available at that scheduler event |
| `as_of_timestamp_ns` | Journal cutoff: snapshot time minus explicit snapshot lag, floored at zero and capped at tape end |
| `response_timestamp_ns` | Client receives that frozen response after response latency, possibly after later venue activity or tape end |

The snapshot uses immutable reports generated by the venue, independently of
whether transport delivered those reports. It carries available original fill
IDs, execution quantities, prices, costs and timestamps, plus optional order state
and the state event time. Snapshot lag models stale history; a per-order fill limit
models incomplete detail, and order state can be omitted. There is no cursor or
automatic pagination. `execution_detail_complete_as_of` describes that order's
available history at the cutoff; it is not a guarantee about later executions.

Historical market activity precedes same-time commands. A zero-delay query sent
by a timer enters the next causal wave; a zero-delay response follows its request
within that wave. Each response is frozen at request arrival. Later fills and
cancellations cannot leak into it at delivery. Client guards reject snapshot,
as-of, state or fill times that exceed their causal or covered cutoff.

```mermaid
sequenceDiagram
    participant C as Stopped client
    participant V as Simulated venue journal
    C->>V: Query sent at 120, request latency 0
    Note over V: Freeze live state and fill 1 as of 120
    Note over V: Fill 2 and cancel occur at 160
    C->>V: Optional second scheduled query at 180
    Note over V: Freeze detail and terminal state as of 180
    V-->>C: Frozen response arrives at 420
    Note over C: Learn fill 1; later fill and cancellation remain unknown
    V-->>C: Detail and terminal state as of 180 arrive at 480
```

The scheduled second query is sent while the first response is still travelling.

## Evidence and accounting

Delivered fill IDs share one deduplication boundary with original execution
reports, repeated query responses and duplicate envelopes. They update known
inventory and a client execution ledger once. The ledger discloses integer tick
cash and exact Decimal fee/rebate totals. Venue cash is booked only by actual
exchange executions; queries never call matching or portfolio accounting.
Fill-table notification time records the earliest delivered source of detail,
which can be a query. Late original reports cannot overwrite it or count it twice.

Delivered order state tightens existing quantity bounds. A terminal state retires
the stop controller's cancellation work but does not invent missing execution
price or cost detail. An older live snapshot cannot undo stronger evidence.
Late original acceptance after query retirement cannot resurrect a cancellation.
The policy sends no extra entries or cancels and resumes no strategy decisions.

An absent order has no terminal implication. An unknown-order cancel rejection,
an empty snapshot, a missing response, or elapsed time alone never releases a
reservation. A stale live state remains uncertain. Truncated fill detail can
establish total executed quantity through terminal state while leaving the client
ledger incomplete. Conversely, complete fill detail without terminal state does
not establish the absence of further fills.

Queries processed after tape end cap their history at tape end and explicitly set
`snapshot_within_tape: false`. They may recover already covered executions, but
cannot resolve later live/travelling order outcomes or uncovered expiry/cancel
arrivals. Covered terminal evidence remains valid for a stable, never-reused order
ID even when delivered later; that order cannot execute again. No absent result
claims that the order never filled.

The existing deterministic fault plan also supports `reconciliation_requests`
and `reconciliation_responses`. Drops produce no receipt; duplicates preserve
logical identity and arrive together. Plans, nominal sends, actual deliveries,
duplicate suppression and pending channels remain disclosed. Comparisons reject
different reconciliation plans. `reconciliation.json` saves query inputs,
generated frozen responses, actual receipts, client knowledge at each query
receipt and the final client execution ledger. Response and request loss remain
visible rather than inferred away.

## Independent evidence and complementary review

The [JSON audit](RECONCILIATION_STRESS_V1.json) covers **168 paired cases / 336
full replays**. All three strategies and both directions use neutralized signals.
The 28 modes cover complete, stale, absent, partial, detail-only, lost and duplicate
responses; delayed requests; response and query horizon boundaries; repeated
queries; late originals; full-fill/cancel races; one-nanosecond trade/cancel
boundaries; live exposure and requests beyond tape coverage.

An independent scalar history derives two external units ahead of four own units,
the first trade's `2+1` budget, subsequent own fills and historical-first cancel
timing. It derives execution identity, state, exact costs, expected query content,
original-report receipts, query envelopes and causal waves without calling the
production exchange, queue, portfolio or journal to obtain expected results.
Observers copy handler inputs and client outputs only. **5,400 checkpoints**
verify client inventory, bounds, reservations, receipts and identity. Final public
fills and cash/marked accounting receive independent arithmetic checks.

Each pair verifies byte-identical order, inventory, P&L, market, quote, risk,
markout and configuration artifacts. Fill economic fields match exactly; the
notification column is allowed to reflect earlier recovery. The audit preserves
each no-recovery run alongside its recovery run.

**Eleven study corruption controls** reject altered knowledge, timestamps,
sequences, future fill detail, incorrect state, missing detail, duplicated fill
identity, wrong client cash and falsely terminal absence. A separate suite of
**72 complementary checks** uses ordinary public-output replays and a different
closed-form witness: three external units ahead of five own units, executing
`2+3` around cancellation. It checks frozen responses across a later full fill,
late originals, equality at the horizon, query/cancel ties, travelling entry versus
absent order, covered/uncovered expiry, and partial taker detail. Four of these
checks inject future evidence at the client boundary. **Five client-only identity
tests** also use different report IDs for one fill and both arrival orders.

The complementary code review found the query-before-original-acceptance ordering
hazard and added the non-resurrection guard. This is a new recovery-path invariant,
not a claimed defect in the prior no-recovery study. Query tests exercise a stopped
client; active strategy reconciliation and recovery-triggered trading are outside
this policy.

## Findings and limits

| Constructed case | Observed knowledge outcome |
|---|---|
| Complete query after covered cancellation | Three previously lost units and terminal state recovered; client becomes complete |
| Query as of 120 delivered at 420 | Learns only the first unit; later fill/cancel at 160 remain unknown |
| Second query as of 180 delivered at 480 | Learns the other two units and terminal state, without double counting the first |
| Terminal snapshot with only the first fill detail | Exact executed quantity is three, known inventory is one, and completeness remains false |
| Full detail with order state omitted | Known inventory is three; future order outcome remains uncertain |
| Query response duplicated or followed by late original reports | Stable fill IDs book client detail once; venue cash never changes |
| Dropped cancel, query after tape end | Covered three units recovered; live residual remains unresolved |
| Dropped entry or stale snapshot before entry arrival | Absent result preserves sent reservations; no assertion that execution never happened |

Across the selected 168 pairs, no-recovery has **162 incomplete client outcomes**
and recovery has **84**. Queries disclose **324 recovered execution units** and
**156 received responses**. **Twelve venue outcomes remain unresolved** in both
policies. These counts characterize the selected constructed cases; they are not
failure probabilities, reliability estimates or profitability evidence. Inventory
remains unliquidated and marks retain their historical provenance.

The journal assumes retention of original simulated execution history; omission
is modeled by prefix limits, absent state or stale cutoffs. There is no calibrated
venue API, retention window, pagination, retransmission, timeout, automatic retry,
response reordering, payload alteration, order-ID reuse, process restart or durable
inbox. Response corruption tests validate guards/oracles; they do not add a corrupt
payload transport mode. Stable terminal identity is an explicit protocol premise.
Selected passive FIFO histories and complementary taker/expiry witnesses do not
prove every tape or venue model.

To replay a saved query case, load its tape/configuration and both plans:

```python
import json
from pathlib import Path
from lobmm.backtest import run_backtest
from lobmm.config import load_config
from lobmm.data.loaders import load_events
from lobmm.reconciliation import ReconciliationPlan
from lobmm.transport import TransportFault, TransportFaultPlan

case = Path("experiments/reconciliation-stress-v1/complete__fixed_spread__1")
faults = json.loads((case / "transport_faults.json").read_text())
raw = json.loads((case / "reconciliation.json").read_text())
plan = ReconciliationPlan(
    tuple(raw["query_timestamps_ns"]),
    raw["request_latency_ns"],
    raw["response_latency_ns"],
    raw["snapshot_lag_ns"],
    raw["fill_limit_per_order"],
    raw["include_order_state"],
)
run_backtest(
    load_config(case / "run_config.yaml"),
    load_events(case / "tape.csv"),
    run_name="repeated",
    reconciliation=plan,
    transport_faults=TransportFaultPlan(
        tuple(TransportFault(**f) for f in faults["faults"])
    ),
)
```
